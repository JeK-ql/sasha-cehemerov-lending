# Дизайн: мультирозмірне замовлення (кілька штук різних розмірів в одному платежі)

**Дата:** 2026-07-14
**Мета:** покупець набирає кількість по кожному з трьох розмірів
(МАЛЕНЬКИЙ/СЕРЕДНІЙ/ВЕЛИКИЙ) і оплачує все одним платежем WayForPay;
менеджер отримує розбивку по розмірах у Telegram.

## Контекст (стан після гілки wayforpay-readiness)

- Замовлення зараз = один розмір × кількість: стан форми `size: Size | ''`
  + `quantity: number`, глобальний степпер [−][ОПЛАТИТИ][+] у `.payRow`.
- Схема (`lib/checkoutSchema.ts`) — єдине джерело валідації для форми і
  `/api/checkout`; тип форми `CheckoutFormState = Omit<CheckoutInput,'size'>
  & { size: Size | '' }`.
- WayForPay-payload будується в `/api/checkout`; `purchaseSignature`
  (`lib/wayforpay.ts`) уже розгортає масиви `productName/Count/Price` — API
  нативно підтримує кілька позицій в одному платежі.
- Telegram-заявка (`formatPendingOrderMessage`) шле `розмір X · ×N`.
- Ліміт 10 штук на замовлення (клієнтська схема + серверний clamp).

## 1. Модель даних

- `sizes: Record<Size, number>` замінює пару `size` + `quantity` у схемі,
  формі й API. Кожне значення — ціле 0–10.
- Валідація (superRefine):
  - сума всіх кількостей ≥ 1 → інакше помилка `sizes`: «Оберіть розмір»;
  - сума ≤ 10 → інакше «Максимум 10 штук у замовленні»;
  - кожен елемент 0–10, цілий.
- `CheckoutFormState` стає рівним `CheckoutInput` (порожня форма —
  `{МАЛЕНЬКИЙ: 0, СЕРЕДНІЙ: 0, ВЕЛИКИЙ: 0}` — валідна за формою типу).
  Експортована назва `CheckoutFormState` ЛИШАЄТЬСЯ як аліас
  (`export type CheckoutFormState = CheckoutInput`), щоб не чіпати імпорти
  в `CheckoutForm`/`OtherDeliveryFields`.

## 2. UI (CheckoutForm)

- Кнопки-сегменти РОЗМІРУ лишаються; тап по кнопці = +1 до цього розміру
  (в межах лімітів). Кнопка з N>0 — інвертована, підпис `НАЗВА ×N`.
- Під `.segRow` — міні-степпер `[−] N [+]` для кожного розміру з N>0
  (у порядку SIZES). «−» до нуля прибирає рядок і знімає інверсію кнопки.
  Степпери — існуюча мова `.qtyBtn`, зменшена (висота ~40px).
- Глобальний степпер у `.payRow` видаляється; кнопка оплати займає всю
  ширину ряду і показує `«{сума} ₴ (×{сумарна кількість})»`.
- Мета-рядок: `OVERSIZE · МАЛЕНЬКИЙ ×2 · СЕРЕДНІЙ ×1` (тільки розміри з
  N>0; жодного розміру — просто `OVERSIZE`).
- Помилка «Оберіть розмір» — у стандартному error-шарі під сегментами
  (після спроби сабміту).
- Заміри: рядок замірів показується під міні-степпером кожного вибраного
  розміру, коли `SIZE_MEASUREMENTS[size]` не null (зараз null — приховано).
- Пульс-анімація ціни (WAAPI) переноситься на інкременти будь-якого розміру.

## 3. Сервер (/api/checkout)

- Clamp по-розмірно (0–10) і сумарно (≤10) — не довіряти клієнту.
- Позиції WayForPay: для кожного розміру з N>0 —
  `productName: 'Футболка - <name> (<розмір>)'`, `productCount: N`,
  `productPrice: PRODUCT.price`. `amount` = сума по позиціях.
- `purchaseSignature` без змін (уже підтримує масиви); додати юніт-тест
  підпису з двома позиціями.

## 4. Telegram

- `PendingOrder`: `size`+`quantity` → `sizes: Record<string, number>`
  (або зведений рядок). Повідомлення:
  `Товар: too much яром too much долиною · МАЛЕНЬКИЙ ×2, СЕРЕДНІЙ ×1`
  (тільки N>0), сума — загальна.
- «✅ Оплату підтверджено» — без змін.

## 5. Тести

- Схема: нуль сумарно ↛ («Оберіть розмір»); сумарно 11 ↛ («Максимум 10
  штук у замовленні»); один розмір ×3 ✓; комбінація 2+1 ✓; від'ємні /
  дробові кількості ↛.
- Telegram: розбивка по розмірах, нульові розміри не згадуються.
- WayForPay: `purchaseSignature` з двома позиціями дає очікуваний HMAC
  (еталон порахувати руками в тесті).

## Не в скоупі

- Облік залишків по розмірах.
- Різні ціни для різних розмірів.
- Кошик з кількома різними товарами.
